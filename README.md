# Why Did Service Level Collapse in the Festive Peak? A Power BI Root-Cause Analysis

![Data](https://img.shields.io/badge/data-simulated-lightgrey) ![Power BI](https://img.shields.io/badge/Power%20BI-DAX-F2C811?logo=powerbi&logoColor=black) ![Chart.js](https://img.shields.io/badge/web-Chart.js-FF6384) ![License](https://img.shields.io/badge/license-MIT-blue)

## Business problem

A customer support operation (Voice, Chat, Email) missed its service-level target on every day of an 11-day festive peak. Leadership wanted to know one thing: was it a forecasting problem, a people problem, or both, and what should change before the next peak?

| | |
|---|---|
| **Who asks** | Head of CX operations, planning team, finance (cost of extra staff) |
| **Data used** | Four months of daily performance by queue: forecast vs actual volume, handle time, required vs available staff, shrinkage, adherence, CSAT, plus an hourly intraday profile |
| **Approach** | Defined the KPIs with the business first (service level, abandon, forecast accuracy, staffing gap, shrinkage vs plan), built a Power BI model with DAX measures, then compared normal days with the peak to separate the causes |

## Recommendation

1. Base the next peak forecast on last year's actual peak, not a flat 15% uplift.
2. Freeze leave and training during the peak window to protect available hours.
3. Plan a temporary batch for the peak instead of stretching the permanent team.
4. Keep breaks and training away from the two daily busy spells (late morning, early evening).

## Findings

| | Normal days | Festive peak |
|---|---:|---:|
| Service level | 82.3% | 54.5% |
| Abandon rate | 3.5% | 8.8% |
| Forecast accuracy | 95.3% | 85.5% |
| AHT | 417 s | 440 s |
| Shrinkage over plan | +1.7 pts | +5.5 pts |
| Days service level met | 56% | 0% |

- Normal days are fine. The trouble is the peak: volume came in about 35% higher but the forecast only planned for 15%.
- It wasn't only volume. Contacts got longer and more people were off the floor, so the staffing gap was bigger than the forecast miss.
- Mondays are the heaviest day, and every queue has two busy spells (late morning and early evening). Keep breaks and training away from those hours.
- For the next peak: base the uplift on last year's actual peak, freeze leave and training for that window, and plan a temporary batch.

## Data dictionary (daily_queue_performance.csv)

| Column | Meaning |
|---|---|
| Forecast_Volume / Offered / Handled / Abandoned | Contacts forecast, arrived, answered, lost |
| Answered_Within_SL / SL_Target | Contacts answered in target time, and the target (80/20 voice, 85% chat, 90% email in 24h) |
| AHT_Sec | Average handle time in seconds |
| Required_FTE / Scheduled_FTE / Actual_FTE | People needed, rostered and actually available |
| Planned_Shrinkage / Actual_Shrinkage | Share of paid time not available for contacts |
| Schedule_Adherence / CSAT | Adherence to schedule, customer satisfaction (1 to 5) |

## Using it in Power BI

The Power BI report is built and running in the Power BI service (two pages: Overview and Intraday). It reads the CSVs in `/data` straight from this repo, so a refresh picks up any change here.

Everything needed to rebuild it is in [`powerbi/`](powerbi/): the two Power Query scripts, the full model as TMDL (calendar, KPI measures, relationship), and a short step-by-step guide with the numbers you should see.

## Run the web version locally

Just open `index.html` in a browser. To regenerate the data: `node generate_data.js`.
